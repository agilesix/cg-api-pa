# ADR 005: Adopt SDK v0.5.0 plugin-owned transforms; retire `IAdapter`

**Status:** Accepted (2026-06-22)

Supersedes [ADR 003](003-integrations-harness.md).

## Context

`@common-grants/sdk` v0.5.0 redesigned `definePlugin()`. The plugin now owns,
in a single declaration:

- custom fields (`schemas.Opportunity.customFields`),
- the source-system schema (`sourceSchema`),
- bidirectional transforms (`toCommon` / `fromCommon`), and
- plugin identity (`meta`, with `capabilities`).

ADR 003 had deliberately kept transforms and the source schema _out_ of the
plugin, behind a local `IAdapter<TSource>` interface, on the grounds that
merging them would break the plugin's use as a pure client-side schema and
force plugin consumers to install the adapter's HTTP-client dependencies. v0.5.0
adopts the merged model upstream, but keeps the HTTP client and storage helpers
_out_ of the plugin — which addresses ADR 003's core objection.

## Decision

**Replace `IAdapter` with the SDK plugin.** `definePlugin()` is now the seam for
schema + source schema + transforms + identity. `src/core/IAdapter.ts` and the
composed `PaAdapter` object (which nothing consumed at runtime) are deleted.

**Transforms are thin; the SDK validates.** `definePlugin()` wraps hand-written
`toCommon` / `fromCommon` with schema validation (`commonSchema` and
`sourceSchema` respectively), folding Zod issues into `TransformResult.errors`.
So our transforms are pure mappers that return `{ result, errors: [] }`; they do
not reference the schema, which keeps `plugin` ⇄ `transform` free of an import
cycle (the only `transform → plugin` edge is a type-only import).

**Operational helpers stay external and minimal.** The pieces the SDK plugin
does not own — `createSourceClient` (just the `PaSourceClient` constructor),
`getSourceId`, and `buildSearchText` — remain plain exports. The former
`buildStoredOpportunity` is replaced by a generic `storedFromCommon()` in the
storage tier that derives every `StoredOpportunity` column from the CG
opportunity, leaving only `sourceId` and `searchText` as per-source inputs.

**No source-binding interface yet.** A named contract bundling
`{ plugin, getSourceId, buildSearchText }` was considered and declined for a
single source — it would be premature abstraction. The planned California
source is the trigger to revisit it against real duplication.

**Dates: keep the string (wire) shape; use the schema only to validate.** The
CG date schemas parse strings into `Date` objects, and the SDK's validated
`toCommon` output returns those `Date`s. Our API serves stored JSON verbatim and
CG single-date events are calendar dates, so we persist the string-shaped output
of the pure builder and use `toCommon` only as the validation gate. The runtime
type (`PaOpportunityInput`, the `z.input` view) is our DTO; `Date` objects are
never served. We do no date arithmetic, so we lose nothing by not materializing
`Date`s.

## Consequences

- Deleted ~95 lines of `IAdapter` plus the unused `PaAdapter`; validation moved
  from a manual `safeParse`-and-throw in the ETL to the SDK's `errors` array.
- A small, localized tax remains from the schema's input ≠ output shapes: two
  `as unknown as` casts in `plugin.ts` and a validate-with-`toCommon` /
  store-with-builder split in `cg.config.ts`. These would disappear if the SDK
  stopped coercing dates to `Date` (validate-and-keep-string); that is the fix
  we would recommend upstream.
- `@common-grants/cg-grants-gov@0.1.0` targets the old API and is broken under
  v0.5.0, so the live cross-plugin alignment test is paused and the dev
  dependency removed; the guard now validates shared-field values against the
  mirrored value schemas. Restore the cross-parse when a 0.5.0-compatible
  release ships (common-grants/ts-cg-grants-gov PR #11).
- `cg check spec` is unchanged by this migration: the same 172 documented
  comparator false-positives (see `docs/known-spec-discrepancies.md`), none
  introduced by the plugin changes.

## Known SDK friction (candidates to raise upstream)

1. Validation forces normalization — there is no "validate but return my output"
   mode, so a transform that emits the calendar-date wire shape has it replaced
   by `Date`-normalized output.
2. The `ToCommon` / `FromCommon` return type wants the `Date`-shaped output while
   the guidance is to return strings, forcing a cast.
3. The functions path requires both `toCommon` and `fromCommon`; an ingest-only
   plugin must author an unused, lossy reverse transform.
4. `toCommon(source)` has no context argument, so run-time values (e.g. the sync
   timestamp) must be generated inside the transform, making it impure.
